# 把自抛接球补到真机：接下来具体做什么

2026-11-23。目标保持为：鸭子自动抛球、向前追、球落地前接回并持续夹稳，提供录像。旧的落地拾取、入箱、归位任务保持独立。

**目前只完成了仿真训练、迁移失败的定位、只读设备检查，以及本次新增的相机取帧工具。真机球追踪、舵机动态测量和通过验证的实机接球策略仍未完成。** 相机工具已用模拟服务验证，没有连接真实相机。不能据此声称已补完视觉闭环。

## 最短顺序

| 顺序 | 要做的事 | 你现场配合什么 | 程序和训练应交付什么 |
|---|---|---|---|
| 1. 让程序拿到图像 | 在板端读取原厂 `mediad` 原始图像，保留尺寸、旋转、时间戳 | 开机、电脑连 WD- 热点，使用这只鸭子已确认的 SSH 账号；开始采集前拿球在嘴前缓慢移动 | 可查看的原始帧、预览、时间记录；取不到时明确报告原因。本次已经准备这个采集入口 |
| 2. 从图像得到球的状态 | 标定相机和嘴的位置关系；识别球并连续估计位置、速度、置信度，补偿头动和图像延迟 | 用实际要验收的球，量直径和质量；拍不同位置、角度的标定板和球，覆盖嘴前、释放点和回接点 | 图像上叠加球轨迹的录像、标定参数、与独立观测对照的误差报告；遮挡/丢球明确标记无效 |
| 3. 测出舵机真实响应 | 查关节映射和限位；在原厂可用的控制/记录通道做嘴、头、颈的小幅动作，记录指令与实测编码器，测延迟、速度、超调和重复性 | 平地放稳、留出活动空间，准备原厂停止入口；测量阶段配合固定机位录像 | 同一板端时钟上的目标、编码器、IMU记录；响应参数和误差范围。匿名状态轮询不够时，先接原厂正式记录接口 |
| 4. 重新训练并自动验收 | 把测出的舵机和视觉限制放回仿真，多鸭并行训练；在板上运行完整感知和控制，再逐阶段试动作 | 放好验收球和侧面录像设备，启动一次并观察 | 独立测试结果、失败样例、自动抛/追/接的真机录像和原始记录 |

前两步的拿球、摆标定板是采集训练依据，不是用人工替代最终动作。最终验收不依靠人在抛球、追球或闭嘴阶段逐次按键。

## 现在就能执行：只读相机采集

先按[现场检查单](self-catch-field-validation.md)开机并连 `WD-` 热点。这台设备的 SSH 账号需要从实际设备或原厂资料确认；Wi-Fi 密码不能用来推断 SSH 账号和密码。脚本会核实热点直连和非演示 Studio 身份，SSH 前再次检查路由。

在这台 Linux 电脑终端执行，替换 `已确认账号`：

```bash
python3 -I -B -S "/home/harrisonwang/文档/ChatGPT/wonder/delivery/selfcatch-camera.pyz" --ssh-user 已确认账号
```

开始命令前，让球在鸭子嘴前的候选抛接范围缓慢移动，持续到采集结束。第一次目的是看清球是否进入画面、是否被嘴遮住；不让鸭子动作。使用这次最终要验收的球，实测直径和质量，不自动把其他球当成原仿真的 20 mm、2.5 g 球。

- 默认请求 30 帧；板端原始像素缓冲上限 128 MiB，取帧总窗口最多 5 秒；取够即停止。时间和内存不足会保留部分记录并返回非成功状态，不自动扩大资源。
- 板端采完后才通过 SSH 传回电脑，降低 Wi-Fi 吞吐对采样过程的影响。时间统计仍包含原厂取帧接口、复制和本工具的开销，不能当成传感器本身的最高帧率。
- 只在板端 Python 标准库中运行取帧程序，不安装依赖、不写板端文件、不打开运动/串口/GPIO接口。只请求 `hello` 与 `media.frame`。首次 SSH 核实主机密钥；密码在终端 SSH 提示中输入。
- 电脑端输出到包旁的新目录 `camera-records/camera-时间/`：`preview.png` 是第一帧的缩小、转正预览，`capture.tar` 保留完整 UYVY 原始帧和帧级时间信息，`report.json` 记录预检与采集结果。
- `FRAME_CAPTURE_ONLY` 仅表示收齐并核对了请求的图像；`CAPTURE_PARTIAL` 表示未取够；`CAPTURE_INCOMPLETE` 表示 SSH、传输或记录校验失败。任何状态都不表示已识别球或接球成功。
- 接口以已审查源码的 API **62** 和 `/run/mediad/media.sock` 为依据。真实镜像版本未核实；版本不同、socket 不存在或账号无访问权限就报告失败，不能通过自动更新固件、改权限或冒用 Studio 客户端来掩盖问题。

## 图像这项什么时候算补完

“浏览器看得到画面”和“接球策略能可靠用这幅画面”是两项验收。正式感知和动作控制应在鸭子本机运行，电脑负责查看与保存记录。

1. **看得见。** 用实际球覆盖释放点、飞行段、回接点，检查焦点、光照、运动模糊、嘴部遮挡。若关键飞行段根本不在头部相机视野内，需要调整可行的抛接轨迹或增加可用视角，再决定方案；不能靠训练补出未观测的信息。
2. **位置对得上。** 使用已知实际尺寸的标定板，采集不同距离、角度的图像，解出内参/畸变；再校准相机到头部、嘴部的坐标关系。头和颈动时，结合对应时刻的关节反馈更新转换。源码里的通用相机参数不能自动算作这只鸭子的实测标定。
3. **速度和时间对得上。** 由连续观测估计三维球状态与不确定度；已知球尺寸只能提供有误差的单目距离估计，需要独立对照。保存图像时间、编码器时间、推理完成时间、命令时间，测端到端图像延迟与动作延迟。
4. **输入只有现实能取得的量。** 目前 PPO 的球位置/速度、身体速度来自仿真。不能把像素坐标直接填进去；需明确坐标系、单位、归一化和有效标记。身体速度也要接入可验证的估计，或改成相对机身的观测并重新训练。必须使用与最终部署一致的观测和时序验证。

原厂源码 `mediad/src/pipeline.rs` 的 `captured_at` 取自图像回调中的 `SystemTime::now()`。它是软件收到缓冲区时的时间，**不是硬件曝光时间**；新采集记录明确标注这一点，端到端视觉延迟仍留空。下一步需要核对设备实际版本和驱动时间语义，结合统一时钟的已知视觉事件，测量曝光到状态估计完成的延迟；不能用电脑接收时刻减板端时间戳就声称完成测量。

## 舵机和策略这项什么时候算补完

先测再训练，避免继续优化一个真机做不到的动作。

- 按这只设备的配置确认关节 ID、角度单位、方向、HOME、软件/机械限位。对嘴、头、颈在已确认的有效范围内分别做小幅往返测量；先测空载，再确认夹球后的差异。这里不预写一个未核实的角度范围并执行。
- 使用实测编码器反馈，不拿“刚发出的目标角”冒充实际到位。同步记录指令到首次运动、到目标附近的时间，打开/闭合速度、死区、超调、负载差异和重复性；用独立录像对照物理运动与接触结果。
- 核对实际控制周期和舵机内部插值。原厂代码明确讨论过舵机的运行时间/限速配置会拖慢动作；不能直接把这些寄存器清零来追求速度。模型应反映这只机器当前可用、已验证的配置。
- 校准模型应能预测未参与拟合的动作响应，再用于训练；把延迟、摩擦、球和相机误差在实测范围内变化。模型不准确时先修模型，不能把“随机化”当成对真实响应未知的替代。
- 多鸭并行强化学习可以继续用，仍保留原任务和旧模型。当前冻结策略在 20 ms 接口上没有通过；迁移微调留出测试也是 **0/100 严格成功**。另外，当前策略每回合只决策两次，是两阶段动作参数策略；持续视觉反馈还需要明确重设计动作更新方式。
- 原仿真短抛的中位飞行时间约 95 ms，源码相机标称 30 fps，粗算仅约 2.85 个帧间隔，尚未扣除曝光、传输、估计和执行延迟。这解释了时序为什么关键；它不证明更高帧率模式可用，也不证明原轨迹在真机可实现。原仿真只移动几厘米，仍不能当成已经实现“跑出去接球”。

建议固定每一轮的独立留出集和判据，报告至少 100 个未用于选模型的起点及全部失败原因。严格成功必须同时包含有效抛起、向前追、接回前未触地、接回后稳定夹持；原有的飞行时长、上升高度、前移和连续夹持门槛保持可追溯。达到仿真发布门槛后，先在板端只计算并记录预测动作，再逐阶段验证站稳、低幅开闭嘴、短抛等实际行为；最终才验收完整连续任务。板端只计算也不能代替实机动作验证。

最后录像要同时看到鸭子和球的全过程，并与动作/感知日志对齐。空中再次碰到嘴、落地后再捡起来、人工在中途补动作，都不算最终目标完成。
